# Weight Transfer Domain Specification

ระบบคัดลอกถอนรหัสค่าน้ำหนักผิวจากโครงสร้างหุ่นจำลองต้นแบบ (Proxy Mesh) ไปยังชิ้นงานจริง ผ่านการหาจุดที่ใกล้ที่สุดบนพื้นผิว 3 มิติจริงของ source แล้วเกลี่ยน้ำหนักแบบ barycentric จากสามเหลี่ยมที่ใกล้ที่สุด ("Closest Point on Surface" ในความหมายเดียวกับ Maya's Closest Point และ ngSkinTools' Transfer Weights)

**Merged domain (2026-07-02):** this domain also owns Export/Import Weight JSON, absorbed from the former `features/data_io/` (now deleted). Import is not a separate code path — it is the exact same transfer engine, with the "source" reconstructed from a JSON file instead of a live mesh. See "Export/Import JSON" below.

## 🧬 Operational Mechanics
ฟีเจอร์นี้เป็นเครื่องมือชนิดพิเศษระดับตริตรองสูง (Weight Transfer) ซึ่งมีพฤติกรรมแตกต่างจากโดเมนอื่นในระบบ:
- **`MERGE` Reads Flattened VGs; `SEPARATE` Reads Each Source Layer's Own Weight+Mask Dicts:** `MERGE` always computes from the source's flattened composite — native `vertex_groups` for a live mesh, or the exported `composite_weights` block for a JSON source — mask synthesized as `1.0` wherever weighted since a flattened composite has no mask concept (one target Layer). `SEPARATE` instead reads the source's own SuperSkinPro Layers one at a time (`ops.py`'s `_get_source_layers()`: `get_meta_list()` + `switch_to_layer()` + `get_active_layer_dict()` + `get_active_mask_dict()` for a live mesh; `io_ops.py` reads the equivalent `layers` array directly out of the JSON) and runs the surface transfer **per source Layer**, scoped only to that Layer's own weight/mask data. Confirmed with the user: when the source has exactly one Layer (or none), `MERGE` and `SEPARATE` produce an identical result — a single target Layer.
- **`CLOSEST_DISTANCE` Is Closest-Point-on-Surface + Barycentric Blend, Not Axial Projection or Nearest-Vertex (rewritten twice after user-reported bugs):**
  - **v1 (axial projection):** projected each target vertex onto the 1D line between the source's first/last vertex-group centers, clamped to `[0, 1]`. Every target vertex got *some* weight no matter how far away it was — a localized source Layer (e.g. `Head`) transferred onto an unrelated target (e.g. a belt) fully occluded every Layer below it.
  - **v2 (nearest source vertex + distance-based mask falloff):** fixed the occlusion bug via a KD-tree nearest-vertex lookup with a synthetic bounding-box-based mask falloff, but this snaps every target vertex to a single source vertex's exact weight value with zero interpolation — when the target has meaningfully more topology than the source, this quantizes a smooth source gradient into flat, kinked bands (visually confirmed: a clean rainbow gradient on a low-poly source came out blocky and creased on a higher-poly target). The synthetic falloff also didn't reflect the source's *actual* mask data, so a fully white-masked source Layer could still leave the target's mask incomplete.
  - **v3 (current) — `transfer_core.closest_surface_point_transfer()`:** built from a world-space `mathutils.bvhtree.BVHTree` over the source's triangulated faces (`transfer_core.build_surface()`, computed once per operator run and shared across every target/Layer since it's purely geometric — either from a live mesh's own vertices/`mesh.loop_triangles`, or from a JSON file's stored `positions`/`triangles`). For each target vertex, `bvh.find_nearest()` finds the true closest point on the source's actual *surface* (not a vertex), and `mathutils.interpolate.poly_3d_calc()` computes that point's barycentric weights against its triangle's 3 vertices. Both the transferred **weight** and the transferred **mask** are barycentric blends of those same 3 vertices' own weight/mask data — smooth wherever the source is smooth (continuous interpolation instead of nearest-vertex snapping), and naturally confined to wherever the source Layer actually has weight+mask (no separate distance-falloff heuristic needed at all, since a triangle with zero weight/mask for this Layer blends to zero automatically).
  - **v3 bug fix — `mask_default`, not a bare `0.0`, is the fallback for a missing mask entry:** `get_active_mask_dict()` only returns vertices *explicitly* painted differently from the layer's own default fill level — a layer filled solid white via a "Fill Mask"-style action never gets a dense per-vertex dict at all, so `layer_mask.get(v_idx, 0.0)` silently treated every such vertex as mask `0.0` and produced a Layer with **zero written vertices** (confirmed via debug log: `create_layer(...) -> verts=0` immediately followed by a full Mask Gap on every target vertex). `core/layer_storage/topology_heal.py`'s own `layer.get("mask_default", 1.0)` is the authoritative fallback (**`1.0`**, not `0.0`). Both `ops.py`'s `_get_source_layers()` and `io_ops.py`'s import path read each Layer's own `mask_default` and thread it into `closest_surface_point_transfer(..., mask_default)`, which uses `layer_mask.get(v_idx, mask_default)` instead.
- **Target Write Goes Through `CoreFacade`'s Layer API:** unlike the source side, the target is written as one or more real SuperSkinPro Layers (visible in the Layer Viewer panel), using `get_ctrl().create_layer(name)` / `switch_to_layer()` / `write_layer_dict()`. `finish()` then reflattens the target's full layer stack back onto its native Vertex Groups (Armature deform), so no manual `vertex_groups.new()`/`.add()` calls are needed for weight data.
  - **`create_layer()` takes only a positional `name` argument** — the old `data_io` domain's call with `visible=`/`mask_default=` kwargs was stale/broken against the current core signature (`TypeError: got an unexpected keyword argument 'visible'`, confirmed at runtime); the canonical, currently-working call site is `features/layer_viewer/ops.py`'s `SUPERSKIN_OT_layer_add` (`ctrl.create_layer(f"Layer {existing}")`), which this domain mirrors.
  - **Structural layer-list mutations (`create_layer`, `remove_layer`, `init_layer_system`) are wrapped in `interface.utils.utils._run_in_object_context(context, callback, *args)`**, the same helper `layer_viewer`'s CRUD operators use — it saves/restores the target's mode around the call since these mutate the mesh's `ss_layers_meta` custom property and require Object Mode.
  - **UI sync is mandatory after any layer mutation:** `sync_layers_to_ui_collection(target)` copies the raw `ss_layers_meta` JSON into `target.superskin_layers_collection`, the collection the Layer Viewer's `template_list` actually reads from. Skipping this call is why the Layer panel showed zero layers even though the weight data had already been written correctly — writing `ss_layers_meta` alone does not refresh the UI-facing collection. `_select_only_layer()` and `_enforce_visualizer_from_tab_state()` are called alongside it to match the highlight/shader state the canonical Add/Remove/Move Layer operators leave behind.
- **No Edit Mode Required:** layer creation/writes happen entirely in Object Mode (mirrors `SUPERSKIN_OT_enter_layer_edit`'s `init_layer_system()` call, which also runs before Edit Mode is entered). Neither operator ever toggles the target into Edit Mode, so neither touches the `__ssp_*` temp VG / undo machinery. (The old `data_io` import operator required Edit Mode; that requirement is gone.)
- **`interface.utils.utils` Is an Allowed Import:** `interface/README.md`'s closed-subsystem rule only forbids importing `interface.panel_main` / `interface.widget_preferences` / `interface.addon_preferences` (layout/panel internals) directly from `features/`. `interface.utils.utils` is a plain helper module, and `features/layer_viewer/ops.py` already imports from it directly — this domain follows that existing precedent.

## 📤📥 Export/Import JSON

Import is literally the same transfer as `object.mw_copy_skin_weight_maya` — same `layer_output` / `insert_method` / `transfer_method` prefs, same `transfer_core` engine — with the source reconstructed from a file. To make that possible, the JSON format stores far more than the old `data_io` domain's format did:

```json
{
  "version": 2,
  "vertex_count": 8,
  "positions": [[x, y, z], ...],
  "triangles": [[i, j, k], ...],
  "composite_weights": {"<v_idx>": {"<bone_name>": weight, ...}, ...},
  "active_layer_index": 0,
  "layers": [
    {"index": 0, "name": "Base", "mask_default": 1.0,
     "weights": {"<v_idx>": {"<bone_name>": weight}},
     "mask": {"<v_idx>": mask_value}}
  ]
}
```

- **`positions` (world-space) + `triangles` are new, and mandatory for `CLOSEST_DISTANCE`.** The old `data_io` format never stored geometry at all — it only made sense for exact vertex-index round-trips. `io_ops.py`'s import validates `"positions" in data and "layers" in data` and reports an error for older files instead of silently misbehaving.
- **`composite_weights` is new** — the flattened native-VG snapshot at export time, used by `MERGE`, exactly mirroring what `ops.py` computes from a live source's `vertex_groups`.
- **v1 files (old `data_io` format) are not forward-compatible.** This is an intentional break, not an oversight — re-export with the current exporter.
- **No configurable export/import settings.** The old `data_io` domain's `export_precision` (IntProperty) and `clear_unmapped_bones` (BoolProperty, already dead — read by nothing) were removed per explicit user request ("เขียนไว้ได้ห่วยแตกมาก... รื้อออกได้เลย คิดว่าไม่จำเป็น"). Precision is a fixed `_PRECISION = 5` constant in `io_ops.py`.
- **Bone-name auto-creation applies to import too:** `transfer_core.ensure_native_vertex_groups()` is called with the union of every bone name referenced across `composite_weights` and all `layers` before any weight write, same as the live-transfer path.
- **`auto_assign_armature` Pref — Armature Auto-Setup for Import Too:** export now also records `armature_name` (the source's bound Armature object's name, or `null` if the source had none). If the `SSPrefWeightTransfer.auto_assign_armature` checkbox is on (default `True`) and the file has a recorded `armature_name`, import looks up `bpy.data.objects.get(armature_name)`; if it's missing or not an Armature, a new empty Armature object is created with that exact name (`bpy.data.armatures.new()` + `bpy.data.objects.new()`, linked into `context.collection`) so the modifier assignment always has something to point at. Either way, `transfer_core.ensure_armature_modifier(target, armature_obj)` — the same helper the live-transfer operator uses — creates/finds the target's Armature modifier and assigns it. A freshly-created empty Armature has no bones (none were exported), so it deforms nothing until the user adds/renames matching bones; this mirrors what the live-transfer operator does when it points a modifier at an existing rig, just without a rig to point at yet.
- **`bl_idname`s are unchanged** (`superskin.export_weight_json`, `superskin.import_weight_json`) even though the implementation moved from `features/data_io/ops.py` to `features/weight_transfer/io_ops.py` — per the project's "Never Edit `bl_idname`" rule, any saved keymaps/macros referencing these still work.

## 🛠️ Configuration Spec (`default_config.json`)
```json
{
  "layer_output": "SEPARATE",
  "insert_method": "REPLACE",
  "transfer_method": "CLOSEST_DISTANCE",
  "auto_assign_armature": true
}
```

| Pref | Options | Behavior |
|---|---|---|
| `layer_output` | `SEPARATE` (default) / `MERGE` | `SEPARATE` creates one target Layer per source Layer (e.g. `Head`, `Arm`, `Base`), **each carrying its own recomputed weight data** scoped to that Layer's bones — not a duplicate of a single global result. `MERGE` always creates exactly one target Layer named `"Transfer from <source_name>"` (or `"Transfer from <filename>"` for JSON import), using the flattened composite of all bones regardless of how many Layers the source has. If the source has no Layer system of its own, `SEPARATE` falls back to a single Layer named after the source object. |
| `insert_method` | `REPLACE` (default) / `APPEND` | `REPLACE` ends up with only the new Layer(s) on the target and clears its native vertex groups before writing. `APPEND` leaves the target's existing Layer stack untouched and only adds the new Layer(s) via `create_layer()` (confirmed to land on top of the stack — see rule 13 below). |
| `transfer_method` | `CLOSEST_DISTANCE` (default) / `VERTEX_ID` | `CLOSEST_DISTANCE` finds the closest point on the source's actual triangulated surface per target vertex (BVH) and barycentric-blends both weight and mask from that triangle's 3 vertices — smooth, and self-limiting to wherever the source itself has data, no distance threshold to configure. `VERTEX_ID` instead copies weights 1:1 by matching vertex index between source and target (requires identical vertex counts — for JSON import, against the file's `vertex_count`), with mask always `1.0` since the correspondence is exact. |
| `auto_assign_armature` | `bool`, default `True` | **Import only** (no effect on the live-transfer operator or on export beyond recording `armature_name`). When on, find-or-create an Armature object named after the source's own bound armature (recorded at export time) and assign it to the target's Armature modifier — see the "Armature Auto-Setup for Import" note above. |

## 🚨 Rules for Agents
1. **Poll Context Guard (live transfer only):** `object.mw_copy_skin_weight_maya` requires selecting at least 2 MESH objects (`len(context.selected_objects) >= 2`); the Active Object is inferred as the target. `superskin.export_weight_json` / `superskin.import_weight_json` only require a single active mesh object.
2. **Armature Requirement (live transfer):** the proxy/source mesh must have an Armature Modifier bound so it can be used as the reference for creating weight groups on the new target. JSON import has no equivalent hard requirement — instead it has the optional `auto_assign_armature` behavior described above, gated by a checkbox, since the source object no longer exists at import time.
3. **`VERTEX_ID` Requires Matching Topology:** if any target has a different vertex count than the source (or, for import, the JSON's `vertex_count`), the operator reports an error and cancels before mutating anything.
4. **Prefs Are Read at Execute Time:** both `ops.py` and `io_ops.py` read `bpy.context.window_manager.superskin_weight_transfer_prefs` directly — the same PropertyGroup, so changing the dropdowns once affects both the live-transfer button and JSON import.
5. **Debug Log Category:** `weight_transfer_feature.py` (dispatch entry), `ops.py`, and `transfer_core.py` (algorithm + Layer-write steps) log through `CoreFacade.debug_log("feature_domains", ...)` — the sanctioned facade wrapper around `DebugLogService`, since features are forbidden from importing `core_subsystems/` directly. Enable via Preferences > Developer / Debug Tools > "Feature Domains" to trace: prefs read, source/target resolution, per-Layer weight counts, layer-system init, layers removed (Replace), and each `create_layer()` call with its resulting slot.
6. **`ss_layers_meta` Auto-Init:** if `_has_layer_system(target)` is `False`, `transfer_core.write_layers_to_target()` calls `get_ctrl().init_layer_system()` first (same guard `SUPERSKIN_OT_enter_layer_edit` uses before entering Edit Mode).
7. **Never Skip `sync_layers_to_ui_collection()`:** any future edit that adds another `create_layer()`/`remove_layer()` call site must also call `sync_layers_to_ui_collection(target)` afterward, or the Layer Viewer panel will silently stay stale.
8. **Name Collisions Are Disambiguated:** `transfer_core.unique_layer_name()` appends a Blender-style `.001` suffix if a chosen Layer name already exists on the target (relevant for `APPEND`, where pre-existing Layers survive into the same name pool).
9. **`SEPARATE` Recomputes Per Source Layer:** for `CLOSEST_DISTANCE`, each source Layer runs its own independent `transfer_core.closest_surface_point_transfer()` pass against that Layer's own weight/mask dicts (the shared `source_surface` BVH is the same for every Layer since it's pure geometry — only the per-vertex weight/mask lookup differs). For `VERTEX_ID`, a source Layer's own dict already *is* the per-vertex weight map (source/target vertex indices are identical, checked earlier), so it's used directly with no recomputation needed, and mask is always `1.0`.
10. **Newly Created Layers Need an Explicit Mask Write, or `check_for_mask_gaps()` Reports Every Vertex as a Gap:** `create_layer()` leaves a Layer with no mask coverage. Writing only `write_layer_dict()` is not enough — `core/ui_controller/layer_crud.py`'s mask-gap check treats every vertex not covered by *any* Layer's mask as unweighted, even if weight data exists. `transfer_core.write_layers_to_target()` must also call `facade.write_mask_dict(mask_dict)` for every non-empty Layer it writes. For `CLOSEST_DISTANCE`, `mask_dict` is the barycentric-blended mask `closest_surface_point_transfer()` already computed from the source's own real mask data — never overwrite it with a blanket `{v_idx: 1.0 ...}`.
11. **Meta-list dicts key the layer index as `"index"`, not `"slot"`:** confirmed against `core/ui_controller/layer_crud.py`'s `init_layer_system()` (`{"name": "Base", "index": 0, ...}`). The old `data_io` domain read `meta.get("slot", -1)` — a stale/broken key lookup that silently always returned `-1` and therefore matched nothing. Always use `m.get("index", -1)`.
12. **`REPLACE` Creates New Layers Before Removing Old Ones:** `transfer_core.write_layers_to_target()` snapshots the pre-existing Layer slots (`old_slots_to_remove`, descending order) but only removes them *after* the replacement Layer(s) already exist. Removing old-then-new (the naive order) can strand one old Layer behind if `core/layer_storage`'s `remove_layer()` refuses to drop the last remaining Layer as a safety rail — this domain must never touch `core/` to work around that, so it sidesteps the guard entirely by never letting the target's Layer count hit zero. Old slots are removed highest-index-first from a static pre-creation snapshot — safe because removing a lower index only shifts *later* (already-processed) indices, never earlier ones still pending removal. `last_slot` is re-read from `ctrl.active_layer_index` after this removal pass since the new Layers' slot numbers shift down once the old ones ahead of them are gone.
13. **`create_layer()` Inserts at the Top of the Stack (confirmed at runtime):** creating `layer_payloads` in their given order therefore comes out reversed on the target (source stack `Head, Arm, Base` → target `Base, Arm, Head`). `transfer_core.write_layers_to_target()` iterates `reversed(layer_payloads)` so the *first* payload is created *last*, landing on top and preserving the source's stack order.
14. **Native Vertex Groups Are Auto-Created, Same Philosophy as the Armature Modifier:** `transfer_core.ensure_native_vertex_groups(target, bone_names)` creates whichever names are missing from `target.vertex_groups` before any weight write — called from `ops.py` (with `source_vg_names`) and from `io_ops.py`'s import (with the union of bone names across `composite_weights` + all `layers`, unconditionally regardless of `auto_assign_armature`). This guarantees `finish()`'s reflatten always has a slot to write into, even on a brand-new target or one with a partially-matching rig. `transfer_core.ensure_armature_modifier(target, armature_obj)` is the equivalent shared helper for the modifier itself — `ops.py` always calls it with the live source's own armature; `io_ops.py` only calls it when `auto_assign_armature` is on.
15. **`mesh.calc_loop_triangles()` Must Run Before Building the BVH:** for a live source, `ops.py`'s `_source_geometry()` triangulates the source mesh (`mesh.loop_triangles`) before handing vertex-index tuples to `transfer_core.build_surface()` → `BVHTree.FromPolygons(..., all_triangles=True)`. `all_triangles=True` is only correct because every polygon handed in is guaranteed to already be a triangle from this step. For JSON import, the triangles are already stored pre-triangulated in the file (exported the same way), so no re-triangulation happens on import.
16. **Barycentric Weights Only Cover a Triangle's Own 3 Vertices:** `poly_3d_calc()` blends exactly the 3 vertices of the nearest source triangle. A source vertex with no entry in `layer_weights` contributes `0` weight (`.get(v_idx, {})`) rather than raising — intentional, lets a Layer's *weight* influence taper off at its own painted boundary. A vertex missing from `layer_mask`, however, is **not** `0` — see rule 10 / the `mask_default` note above: it falls back to that Layer's own `mask_default` (`.get(v_idx, mask_default)`), never a bare `0.0`.
17. **`data_io` No Longer Exists:** `features/data_io/` was deleted entirely as part of this merge (2026-07-02). Its two operators live on, unchanged by `bl_idname`, inside this domain's `io_ops.py`. Do not recreate `features/data_io/` — any future export/import work belongs here.
